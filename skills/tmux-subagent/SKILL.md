# Coding subagents via pi-tmux

Use the `tmux_*` tools, not `/tmux` (that command is a human-facing picker). This workflow needs a locally installed tmux, the pi-tmux extension, and the chosen agent CLI already installed and authenticated. If any prerequisite is missing, ask for a choice or report the blocker; do not silently switch agents.

1. Agree on the agent, task, repository/worktree, file ownership, expected deliverable, and whether the subagent may edit files or run commands. Prefer a separate worktree for parallel work; if using a worktree, create it under `~/code/agent-workspace/<origin_folder_name>/<worktree>` (for example, `~/code/agent-workspace/pi-tmux/issues-11`, where `pi-tmux` is the original repository folder name) before launching the subagent. Never let two agents edit the same files concurrently. Review the user's constraints before delegating. Do not give the subagent secrets or unrestricted permission to bypass approvals.

2. **Pi is the selected agent: prefer the structured Pi subagent tools.** Call `tmux_subagent_start_pi` with an absolute existing `cwd` (the agreed worktree) and a bounded `task` stating scope, constraints, completion criteria, and where to leave a concise report; optionally pass a readable `name`, a `parent` tmux session, and a safe `model`/`thinking`. The tool creates the durable `SubagentJob`, creates and owns a dedicated detached tmux session, records the stable session/pane IDs on the job, always loads the packaged child completion reporter, delivers the task without shell interpolation, and returns immediately with `jobId`, `status`, `tmuxSessionId`, and `tmuxPaneId`. Do **not** hand-drive `pi` through `tmux_create_session` + `tmux_send_text` when this tool is available, and do not pass flags that bypass approvals or sandboxing.

3. **Any other agent (Claude Code, Codex, OpenCode): use the manual flow.** Prefer a dedicated new window in the session Pi runs in: call `tmux_create_window` without `session` and with the agreed absolute `cwd`. `tmux_list_sessions` marks that session `current: true`; an attached client may view another session. Outside tmux, ask for an explicit session instead of guessing. Create a detached session with `tmux_create_session` only if the user explicitly requests one. Record the returned stable window/session and pane IDs; use `tmux_list_panes` if needed. Do not target an existing human-owned pane. If creation reports `tracked: false`, treat provenance as uncertain and do not assume confirmation-free access. Start the selected CLI in that pane via `tmux_send_text` followed by a separate `tmux_send_key` with `Enter`: `claude`, `codex`, or `opencode`. These are examples, not guaranteed CLI flags or installed binaries. Avoid shell interpolation of untrusted text; send the task to the agent's interactive prompt separately after checking its screen.

4. Deliver the bounded prompt stating scope, constraints, completion criteria, and where to leave a concise report (changed files, tests and their exit status, unresolved issues). For a manual agent, send text literally, then send `Enter` separately. Only send further input after inspecting the pane; never guess what an interactive confirmation means or automatically accept permission prompts. Ask the user when an approval or unexpected action needs authorization.

5. Monitor. For a Pi subagent, prefer `tmux_subagent_status` — it returns the durable lifecycle state (`created`/`starting`/`running`/`completed`/`failed`/`cancelled`/`lost`) and reconciles an obviously vanished target to `lost`; never infer completion from pane text. For any agent you may also use `tmux_capture_pane` (optionally with recent scrollback), but it is a snapshot, **not** proof of completion or success; terminal output may be partial, truncated, or contain secrets. Do not copy sensitive capture content into the final reply. If stuck, timed out, or the agent asks for input, inspect and report rather than blindly repeating keystrokes.

6. Independently verify deliverables in the agreed worktree: inspect the diff and file contents, run appropriate tests and check actual exit codes using normal command tools. A subagent's claim, a durable `completed` status, or a tmux snapshot alone is insufficient — the child reporter records Pi's own outcome, so still verify the actual work. If the task cannot be verified, describe exactly what is missing. Do not merge or overwrite work without the user's authorization.

7. Report the results and verification. Keep the created window or session available for inspection unless the user asked for cleanup. To stop a Pi subagent, use `tmux_subagent_cancel` with its `jobId`: it cancels exactly that job and kills only the stable tmux target recorded on it, and is idempotent if the child already finished. For a manual agent, kill only the stable window or session you created and recheck its identity before doing so. Never kill an unrelated session or pane.
