# Coding subagents via pi-tmux

Use the `tmux_*` tools, not `/tmux` (that command is a human-facing picker). This workflow needs a locally installed tmux, the pi-tmux extension, and the chosen agent CLI already installed and authenticated. If any prerequisite is missing, ask for a choice or report the blocker; do not silently switch agents.

1. Agree on the agent, task, repository/worktree, file ownership, expected deliverable, and whether the subagent may edit files or run commands. Prefer a separate worktree for parallel work; never let two agents edit the same files concurrently. Review the user's constraints before delegating. Do not give the subagent secrets or unrestricted permission to bypass approvals.
2. Create a dedicated detached session with `tmux_create_session` and an existing absolute `cwd` (the agreed worktree). Record its returned stable session and pane IDs; use `tmux_list_panes` if a pane ID is needed. Do not target an existing human-owned session. If creation reports `tracked: false`, treat provenance as uncertain and do not assume confirmation-free access.
3. Start the selected CLI in that pane via `tmux_send_text` followed by a separate `tmux_send_key` with `Enter`: `claude`, `codex`, `pi`, or `opencode`. These are examples, not guaranteed CLI flags or installed binaries. Avoid shell interpolation of untrusted text; send the task to the agent's interactive prompt separately after checking its screen. Do not use flags that skip approvals or sandboxing. For nested Pi, load the packaged child reporter (`--extension <package-root>/extensions/child-reporter.ts`) with the documented `PI_TMUX_SUBAGENT_JOB_ID`, `PI_TMUX_SUBAGENT_STATE`, and `PI_TMUX_PARENT_SESSION_ID` environment so completion is durable, and pass `PI_TMUX_SUBAGENT_ANCESTORS` so a child cannot delegate back into the same parent/job and form a loop (see the "Pi child completion reporter" section in the README).
4. Give the agent a bounded prompt stating scope, constraints, completion criteria, and where to leave a concise report (changed files, tests and their exit status, unresolved issues). Send text literally, then send `Enter` separately. Only send further input after inspecting the pane; never guess what an interactive confirmation means or automatically accept permission prompts. Ask the user when an approval or unexpected action needs authorization.
5. Monitor with `tmux_capture_pane` (optionally include recent scrollback). It is a snapshot, **not** proof of completion or success; terminal output may be partial, truncated, or contain secrets. Do not copy sensitive capture content into the final reply. If stuck, timed out, or the agent asks for input, inspect and report rather than blindly repeating keystrokes.
6. Independently verify deliverables in the agreed worktree: inspect the diff and file contents, run appropriate tests and check actual exit codes using normal command tools. A subagent's claim or a tmux snapshot alone is insufficient. If the task cannot be verified, describe exactly what is missing. Do not merge or overwrite work without the user's authorization.
7. Report the results and verification. Keep the session available for inspection unless the user asked for cleanup; kill only the stable target you created and recheck its identity before doing so. Never kill an unrelated session or pane.
